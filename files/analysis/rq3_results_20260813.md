# RQ3: results (corpus-corrected, 2026-08-19)

**Status:** complete for tests 1, 2 and 4, run on the **code-stripped**
corpus. Two corrections were applied since the first analysis, in this order:

1. A construct-validity screen invalidated the original Affect headline.
2. A corpus-normalisation defect was then found that explained the Affect
   result mechanically, and independently confounded every other dimension.

Anything reporting "LLMs use more negative/sad language, especially for Java"
is withdrawn. Anything reporting "LLM writes longer sentences" is also
withdrawn, that finding **reversed direction** after the corpus fix.

---

## 1. The corpus defect (root cause)

The human and LLM corpora were never normalised the same way.

Human READMEs were extracted via `confirmatory_preprocessor.extract_prose`
(`rq3_extract_java.py:616`), which routes markdown through `_md_to_text` →
`_html_to_text`, decomposing `<code>`, `<pre>`, `<script>`, `<style>` and
others. Fenced and inline code are removed. **LLM output was written straight
from the API response and read back verbatim, no normalisation at all.**

Measured code share of word content in the original LIWC input:

| Corpus | code share |
|---|---|
| java human | 0.8% |
| python human | 2.4% |
| java sonnet | 36.3% |
| java openai | **53.1%** |
| python sonnet | 40.7% |
| python openai | **55.6%** |

So roughly half of every LLM "document" LIWC scored was source code, against
~1–2% on the human side.

**This mechanically explains the Affect result.** 93% of the `java` tokens in
GPT's Java documents sat *inside code blocks*, `import java.util.List;`.
The `emotion`/`emo_neg`/`emo_sad` effect (δ ≈ 0.75–0.95, Holm-corrected,
replicated across both models) was import statements being scored as sadness.

**Fix:** `src/generation/rq3_build_libraries_csv_prose.py` applies the *same*
`_md_to_text` function to the LLM output, reusing the human pipeline's own
function rather than a hand-rolled regex, so both sides receive identical
treatment. Residual code across the whole corpus: **0.049%** (was ~45% on the
LLM side). All 100 libraries retain their full human/sonnet/openai triple.

Verification that the artefact cleared:

| | before | after |
|---|---|---|
| `emo_sad`, java/openai (mean) | 4.148% | **0.024%** |
| `emotion`, java/openai (mean) | 4.286% | 0.181% |
| corr(`emo_neg`,`emo_sad`) on LLM docs | 0.97–0.995 | collapse gone |
| `java` tokens per 100w, java/openai | 2.27 | 0.35 |
| `java` tokens per 100w, java/human | 0.00 (raw comparison) | 0.58 |

Note the last row: post-strip, **human READMEs say "Java" more often than the
LLM does**. The direction reversed once import statements were removed.

## 2. Test 1: does the LLM write differently from the human author?

**14/60 cells pass** (was 22/60). Restricting to the five dimensions the
construct-validity audit rated **clean**:

| Axis | Dimension | java/sonnet | java/openai | python/sonnet | python/openai | Passes |
|---|---|---|---|---|---|---|
| Style | `BigWords` | +0.74 | +0.82 | +0.64 | +0.87 | **4/4** (LLM higher) |
| Style | `WPS` | −0.39 | −0.56 | −0.22 | −0.35 | 3/4 (human higher) |
| Style | `ipron` | +0.32 | −0.05 | −0.22 | −0.59 | 1/4 (human higher) |
| Cognition | `tentat` | +0.04 | −0.16 | −0.03 | −0.02 | 0/4 |
| Cognition | `certitude` | +0.08 | −0.22 | −0.08 | −0.33 | 0/4 |

**`BigWords` is the result of RQ3.** Large effect, same direction, all four
model×ecosystem families, on a dimension validated structurally to ±0.7pp,
and it survived the corpus fix essentially intact. LLM documentation uses
markedly more long/Latinate vocabulary than the documentation real
maintainers write.

**`WPS` reversed direction.** On the raw corpus it read "LLM writes longer
sentences" (2/4, δ up to +0.48). On the clean corpus it is **human higher**
(3/4, δ −0.35 to −0.56). Code lines were being parsed as very long sentences.
The corrected finding is that **human authors write longer sentences.**

Taken together the Style axis does *not* say "the LLM is more formal." It says
something more specific and more interesting: **the LLM packs longer words
into shorter sentences.** Dense, noun-heavy, declarative. That is a coherent
register description, but it is non-monotonic on the axis, so under the original plan
rule ("≥2 dimensions, same direction") it does **not** support a single
axis-level formality claim. `WPS` and `ipron` do agree in direction
(human higher), but `ipron` passes only 1/4.

Six further cells pass on dimensions rated **mixed** or **register-shifted**
(`curiosity` ×2, `achieve`, `motion`, `conflict`, `emo_anger`), all
LLM-higher, all Python-side except two. These are reportable only with their
audit verdicts attached; `motion` (function-return language), `conflict`
(function *arguments*) and `emo_anger` in particular cannot be read at face
value.

## 3. Test 2: is the gap ecosystem-dependent?

**2/30 cells pass** (was 7/30), and both are the same dimension:

| Model | Dimension | Verdict | δ | Magnitude | Direction | Holm p |
|---|---|---|---|---|---|---|
| sonnet | `ipron` | **clean** | 0.452 | medium | java gap larger | 1.5×10⁻³ |
| openai | `ipron` | **clean** | 0.429 | medium | java gap larger | 3.3×10⁻³ |

This is a genuine, cross-model-replicated, ecosystem-dependent effect on a
construct-clean dimension, the LLM's departure from human impersonal-reference
usage is larger for Java than for Python. It is a single dimension, so it
supports a **per-dimension** claim, not an axis-level one.

The Affect dimensions that previously carried test 2 are gone entirely.

Brown-Forsythe (Levene centred on the median), within ecosystem,

|---|---|---|---|
| `tentat` | 3/4 | 0.55–0.57 | human more spread |

**6 of 7 significant cells show the human corpus more spread**, and the one

The finding is weaker than on the raw corpus (SD ratios 0.55 vs 0.42 for

on a construct-clean dimension.

## 5. Answer to RQ3

**RQ3:**

> *Do psycholinguistic profiles of LLM-generated API documentation match the
> human-written profile for the same library, and if they don't, does the
> LLM's deviation from human writing depend on ecosystem (Java vs Python)
> or not?*

### Outcome, against the plan's the RQ3 plan criteria

| Outcome | Criterion | Verdict |
|---|---|---|
| **A** | no axis has ≥2 dims clearing test 1 in either ecosystem | **ruled out**: java/Style 2, java/Drives 2, python/Style 3, python/Action 2 |
| **B** | an axis clears test 1 in a consistent direction in *both* ecosystems, test 2 does not clear | **not satisfied**: no axis has ≥2 same-direction dims in both ecosystems; Style splits (`BigWords` LLM-higher vs `WPS`/`ipron` human-higher) |
| **C** | test 2 clears for a dimension that also clears test 1 in ≥1 ecosystem | **SATISFIED** via `ipron` |

**Answer: Outcome C, the LLM's deviation from human writing is
ecosystem-dependent.**

`ipron` clears test 2 on **both** models (δ = 0.452 sonnet / 0.429 openai,
medium, Java gap larger, Holm p = 1.5×10⁻³ / 3.3×10⁻³) and clears test 1 in
python/openai (δ = −0.595, large, human higher). It is rated **clean** by the
construct-validity audit.

Two qualifiers on the outcome label:

- C rests on a **single dimension**. The RQ3 plan criteria do not require an
  axis-level result for C, but the evidential weight differs from an
  axis-level claim.
- The **largest** effect in RQ3 (`BigWords`, δ 0.64–0.87, 4/4 families) is
  ecosystem-*independent*. So the formal outcome is C while the dominant
  single effect is B-like. Both are true.

### Substantive description

Summary:

> **LLM-generated documentation does not match the human-written profile for
> the same library. It uses markedly more long/Latinate vocabulary
> (`BigWords`, large effect, 4/4 model×ecosystem families, both models),
> delivered in shorter sentences (`WPS`, human higher, 3/4), and it is less
> variable between libraries than human writing, 6 of 7 significant
> dispersion differences show the human corpus more spread, with hedging
> (`tentat`) at roughly half the human standard deviation across 3 of 4
> families. The deviation is ecosystem-dependent on one construct-clean
> dimension: the LLM's departure from human impersonal-reference usage
> (`ipron`) is significantly larger for Java than for Python, replicated
> across both models. On the remaining dimensions, including the largest
> effect, the deviation is ecosystem-independent. Where 100 human-written
> READMEs span a wide stylistic range, the LLM converges toward one voice.**

## 6. Methodological findings worth reporting in their own right

These are outcomes of the analysis, not just corrections:

1. **LIWC affect dimensions are unusable in this register**, demonstrated
   twice independently: `emo_anger` unexplained on RQ1's confirmatory corpus
   (curated stems reproduced 1/28 of the score), and `emotion`/`emo_neg`/
   `emo_sad` on RQ3 reducible to the token `java` at r = 0.854, vanishing
   when code was removed. Most work asserts this as a limitation; here it is
   quantified.
2. **Corpus normalisation must be symmetric, and asymmetry is silent.** The
   defect produced large, significant, Holm-corrected, cross-model-replicated
   effects. Nothing in the statistics flagged it. Cross-model replication in
   particular gave false assurance: both models share the habit of emitting
   code blocks, so both reproduced the artefact faithfully.
3. **The axis rule assumes independence it does not have.** `emo_sad` ⊂
   `emo_neg` ⊂ `emotion`, so one effect satisfies "≥2 dimensions, same
   direction" on its own. The rule should require non-nested dimensions.
4. **Curated-stem construct validation is weak.** It has false positives
   (`cry\w*`→crypto, `miss\w*`→mission, `issue\w*`→issuer), and structurally
   can only say "my list doesn't explain this", never what does. Data-driven
   token recovery (`rq3_affect_token_check.py`) found the real driver in one
   step where curated stems had reached only "murky".

## 7. Limitations

- n=50/ecosystem, two ecosystems, two models, README genre, single prompt.
- 14 documents fall under 100 words after code removal; **all 14 are human**
  READMEs. Percentage-based dimensions are unstable at that length.
- Residual code 0.049%, concentrated in 5 documents (4 human), from indented
  fences inside list items that `markdown` does not treat as fenced code.
  Left in deliberately: matching the human pipeline exactly matters more than
  perfect stripping.
- **Task asymmetry.** The human wrote a README knowing the library, for
  adoption (badges, install, licence, contributing). The LLM wrote from API
  signatures alone. Some measured "authorship" difference is task difference.
  This is inherent to the design and cannot be corrected post hoc.
