# odoo14-addon-sale-exception

A collection of Odoo sales extensions centered on sales-order control, exception handling, pricing, invoicing, delivery, stock, workflow automation, and related customer-service processes.

The library extends Odoo model classes such as sales orders, sales-order lines, products, pricelists, partners, stock moves, invoices, companies, and configuration settings. It also provides transient wizard models, scheduled-processing entry points, portal/controller integrations, and installation or migration hooks.

Although many components are designed to work independently, they commonly relate through the sales-order lifecycle:

1. Configure company-, partner-, product-, pricelist-, workflow-, or order-type behavior.
2. Create and edit sale orders and lines.
3. Apply validation, exception, stock, packaging, pricing, and delivery rules.
4. Confirm orders, generate deliveries, invoices, plans, bookings, or automated workflow jobs.
5. Use wizards and actions to resolve exceptions and perform assisted operations.

## Main capabilities

### Sale-order exceptions and confirmation control

The core exception-oriented API extends `SaleOrder` with checks around confirmation and draft transitions.

| Class | Public methods | Purpose indicated by API |
|---|---|---|
| `SaleOrder` | `detect_exceptions()` | Detect applicable exceptions on sale orders. |
| `SaleOrder` | `test_all_draft_orders()` | Run exception-related checks for draft orders. |
| `SaleOrder` | `sale_check_exception()` | Perform a sale exception check. |
| `SaleOrder` | `action_confirm()` | Confirm an order, potentially subject to extension rules. |
| `SaleOrder` | `action_draft()` | Return an order to draft, potentially subject to extension rules. |
| `SaleOrder` | `write(vals)` | Update order values while applying extension behavior. |
| `SaleExceptionConfirm` | `action_confirm()` | Wizard action for confirming an exception-related operation. |
| `SaleOrderCancel` | `action_cancel()` | Wizard action for cancelling an order with a reason. |
| `SaleMassCancelOrders` | `action_mass_cancel()` | Wizard action for cancelling multiple orders. |

Supporting models include `ExceptionRule`, `ResCompany`, and `ResConfigSettings`, indicating that exception behavior can be defined and configured.

An additional order-level exception is available through:

```python
order.exception_partner_can_order_manufactured_for()
```

on the `SaleOrder` extension supplied by the manufactured-for partner exception component.

## Usage examples

The following examples illustrate calls against Odoo recordsets. The exact way records are obtained depends on the calling context—for example, a server action, wizard, controller, test, scheduled job, or custom module.

### Detect and check sale-order exceptions

```python
# `order` is a SaleOrder recordset.
order.detect_exceptions()

# Perform the explicit exception check.
order.sale_check_exception()

# Continue with the normal confirmation action when appropriate.
order.action_confirm()
```

For a batch process operating on draft orders:

```python
# `orders` is a SaleOrder recordset containing draft orders.
orders.test_all_draft_orders()
```

### Refresh cached pricelist data

Refresh cache entries for a specified group of products and pricelists:

```python
# `cache` is a PricelistCache recordset.
# `product_ids` and `pricelist_ids` are optional values accepted by the API.
cache.update_product_pricelist_cache(
    product_ids=product_ids,
    pricelist_ids=pricelist_ids,
)
```

Build the complete cache:

```python
cache.create_full_cache()
```

Retrieve cached prices for a pricelist and a product collection:

```python
prices = cache.get_cached_prices_for_pricelist(
    pricelist=pricelist,
    products=products,
)
```

A scheduled operation can reset the cache through:

```python
cache.cron_reset_pricelist_cache()
```

### Create an invoice plan

```python
# `order` is a SaleOrder recordset.
order.create_invoice_plan(
    num_installment=3,
    installment_date=first_installment_date,
    interval=1,
    interval_type="month",
    advance=0,
)
```

Remove existing plan entries:

```python
order.remove_invoice_plan()
```

Create invoices from a planned-invoice wizard:

```python
# `wizard` is a SaleAdvancePaymentInv transient recordset.
wizard.create_invoices_by_plan()
```

### Add a product set to an order

```python
# `wizard` is a SaleProductSetWizard transient recordset.
wizard.add_set()
```

To prepare a line explicitly from a set line:

```python
line_values = set_line.prepare_sale_order_line_values(
    order=order,
    quantity=2,
    max_sequence=10,
)
```

### Blocked-order resolution workflow

The stock-block wizard exposes alternative corrective actions:

```python
# `wizard` is a SaleOrderBlockWizard transient recordset.

# Confirm the current wizard operation.
wizard.confirm()

# Or adjust quantities before continuing.
wizard.action_adjust_uom_quantity()
wizard.action_adjust_packaging_quantity()

# Or move affected content to a new order.
wizard.action_move_to_new_order()
```

### Generate lots for an order

```python
# Generate lots at order level.
order.generate_lot()

# Or create a lot for an individual sale line.
lot = order_line.create_lot(index_lot=1)
```

### Work with planner-calendar events

```python
# `event` is a CalendarEvent recordset.

# Navigate to the related sales order.
action = event.action_open_sale_order()

# Mark the event as done.
event.action_done()

# Open the associated invoices.
invoice_action = event.action_open_invoices()
```

### Run automatic workflow processing

```python
# `job` is an AutomaticWorkflowJob recordset.
job.run_with_workflow(sale_workflow)

# Execute the job using its configured processing behavior.
job.run()
```

### Invoke scheduled operations

Several public methods are intended for scheduled execution:

```python
cache.cron_reset_pricelist_cache()

calendar_event.cron_update_dynamic_final_date()

sale_order.cron_sale_validity_auto_cancel(company_ids=company_ids)

reassign_wizard.cron_unsubscribe(date=run_date)
```

## Hooks and migrations

The library exposes Odoo lifecycle hooks and migration functions, including:

- `pre_init_hook(env)`
- `post_init_hook(env)`
- `uninstall_hook(env)`
- `migrate(cr, version)`
- `migrate(env, version)`
- `populate_unrevisioned_name(env)`
- `set_default_partner_product_filter(env)`

These functions are lifecycle entry points. They are normally invoked by Odoo during installation, uninstallation, initialization, or migration rather than called from regular business code.

## Extension model conventions

Most classes inherit from either:

- `models.Model` for persistent business records,
- `models.TransientModel` for wizard and temporary interaction records, or
- `models.AbstractModel` for reusable model behavior.

Many classes intentionally expose no standalone methods. These classes still participate in the public extension surface by adding or adapting model behavior, fields, views, reports, configuration, or business rules through Odoo inheritance.

When extending this library, prefer calling the documented public action and helper methods on recordsets and preserve Odoo’s usual multi-record semantics for methods such as `create`, `write`, `copy`, `unlink`, and `action_confirm`.
